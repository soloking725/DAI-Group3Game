# Plotline Editor — Design Plan

> **Status (2026-08-03): tooling built.** `editor/plotline_editor.html`/`.js`
> ships all four tabs below (Flag Graph / Visions / Quests / Dialogue) plus an
> Export/Save tab, backed by `game/{visions,quests,npcDialogue,storyFlagMeta}.js`
> and the shared analyzer `game/plotlineVerify.js` (cycle / dead-flag /
> unwritten-flag audits). Persistence is the localStorage-override + paste-ready
> export pattern, not new `save-server.js` routes (see §"save-server.js has no
> code path" in the review — the export flow needs none). **Still open**, per the
> build-order §5 and review gaps below: none of the new `game/*.js` are wired into
> `index.html` (runtime doesn't consume them yet); the player-facing quest toast,
> `LORE_ENABLED` vision gating, `npcState` save/load/reset paths, the
> `companionRestricted` region field, and the `debug_v1.html` R-check are all
> game-code/content work the tooling now unblocks but does not itself perform.
> The rest of this doc is the original design plan, kept as the spec.

## Why this exists

Stillpoint's narrative state today is three separate, disconnected systems:
`CUTSCENES{}` (single scripted sequences), a flat `storyFlags{}` namespace with
no structure, and per-room `loreFragments` (currently text, moving to
visions). Nothing tracks a flag's dependents across files, nothing models a
multi-stage relationship with an NPC across rooms, and nothing exists yet for
branching dialogue. This is fine at 3 cutscenes. It stops being fine once the
Child's arc, the Temporal Warden, and a new pacifist-region ally all have
state that interacts — a player finishing "talk to the pacifist NPC 5 times"
needs to be legible next to "the Child was left at the Echo Bridge" next to
"the Temporal Warden's rift closed," and today none of that is visible in one
place or even representable in the data model.

This plan covers four sub-systems, designed together because they share
underlying primitives (flags, ally/NPC state, room-scoped triggers):

1. **Story Flag Graph** — visibility layer, not new authoring.
2. **Lore Vision format** — replaces text lore fragments; new lightweight step type.
3. **Quest/side-objective data model** — first-class multi-stage tracked arcs.
4. **NPC dialogue tool** — branching, re-enterable conversations with talk-count gating.

All four ship as tabs in one new tool, `editor/plotline_editor.html`, following
`Plans/editor_design_style_guide.md` conventions (shared `design-system.css`,
same shell as `cutscene_editor.html`).

## Decisions already made (per user, 2026-08-03)

- The "time ally" is the **existing Temporal Warden** (`chrono_ally` miniboss,
  `game/enemy.js`) — no new character to design, just plotline tracking around
  what's already built.
- The pacifist-region NPC is **new, no name yet**, briefed as: lives in the
  Pacifist Enclave; **the Child cannot be brought all the way into the
  region** (left at the entrance — a gating mechanic, not the same as the
  permanent Void Tether leave); the player **plays games there, including one
  specific game with this NPC**; talking to them enough unlocks **safe
  rest/sleep** in the region; sustained relationship lets the player
  **recruit them as an ally for a later plotline**; they function as an
  **alternate field ally for players who lose the Child** by whatever path.
- The Child's Protect/Train/Leave arc stays **track-only** — this plan adds
  plotline/quest/flag visibility around her existing `companionState`
  (`game/companion.js`), it does **not** build out the missing leveling/path
  mechanics (XP, path-specific passives, revive-on-death) that `story.md`
  describes in prose only. That's separate future work.
- Lore visions are a **new lightweight format**, not reused `CUTSCENES{}`
  steps — short, near-wordless, no input-locked choices, authored in the same
  visual tool as lore placement rather than in `cutscene_editor.html`.

## 1. Story Flag Graph

Read-mostly, derived, not hand-authored — same philosophy as
`Plans/room_progress.js` deriving room state instead of trusting a stale doc.

- **Nodes**: every key in `storyFlags{}`, every `CUTSCENES{}` id, every
  `area.cutsceneTriggers[]` entry, every `QUESTS{}` stage (see §3), every NPC
  dialogue node that sets/reads a flag, and ally-state fields
  (`companionState.active`/`canFight`, the new pacifist-ally state, Temporal
  Warden defeat state).
- **Edges**: generated by static-scanning `game/cutscene.js`, `game/quests.js`
  (new), `game/npcDialogue.js` (new), `game/companion.js`, and
  `game/game_update.js` for `storyFlags.x = ...` (writes) and `storyFlags.x`
  reads (including `if (storyFlags.x)` and template calls). Don't hand-author
  this graph — a hand-authored graph goes stale the moment someone adds a
  `setFlag` step, exactly the failure mode `room_design_bible.md` already
  warns about for static tables.
- **Layout**: force-directed, dynamic (the "look" requested) — flags cluster
  near what sets/reads them; drag to pin. Color by category (cutscene-set /
  quest-set / dialogue-set / ally-state).
- **Editable surface is thin, on purpose**: per-flag description/notes, and a
  rename-across-all-references action. It does not let you add/remove flags
  or edges directly — that stays the job of `cutscene_editor.html`,
  `quests.js`, and the dialogue tool. This avoids the graph becoming a second,
  divergent source of truth.
- **Persistence**: new `POST /save-story-flags` route in
  `editor/save-server.js`, same line-patch + timestamped `.bak` pattern as the
  existing HUD/inventory routes, writing to a new sidecar
  `game/storyFlagMeta.js` (`{ flagName: { description, addedBy } }`) — never
  the flags themselves, which stay wherever they're actually set in game code.

## 2. Lore Vision format

Replaces the plan to keep `loreFragments[].text`. `game/game_entities.js`
already has a partial hook for this — `lf.mode === 'cutscene'` visually rings
the pip differently and (per its own comment) already triggers different
pickup behavior in `game_update.js` — so this extends an existing seam rather
than inventing one from nothing.

- New data shape per fragment: `{ id, x, y, mode: 'vision', visionId }`,
  `visionId` pointing into a new `VISIONS{}` table (own file,
  `game/visions.js`, bare-top-level like `cutscene.js` since other files need
  direct read access, per CLAUDE.md's IIFE-vs-bare convention).
- **Vision step subset** (deliberately smaller than `CUTSCENES{}`'s 8 types):
  `wait`, `cameraPan`, `imageReveal` (single full-bleed image/sprite layer,
  fade in/out — no dialogue box), `setFlag`, `call`. No `choice` — visions are
  non-interactive by design (matches "wordless" brief). Input is locked same
  as a cutscene, but hold-to-skip still works (reuse the cutscene skip path,
  don't reimplement it).
- **Authoring UI**: a tab in `plotline_editor.html` — pick/upload the
  image/sprite layer(s), set pan/hold/fade timing, preview inline (a real
  improvement over `cutscene_editor.html`'s "cheap mocked walkthrough," since
  a vision has no branching to fake — a straight-line preview is actually
  accurate here).
- **Persistence**: `POST /save-visions` route, writes `game/visions.js`
  (patch-and-backup pattern) and any uploaded imagery through the existing
  `POST /save-art-image` route (`assets/art/...`) — reuse, don't duplicate.
- **Placement**: fragment `x`/`y`/`mode`/`visionId` stays authored in
  `room_scene_editor.html` (it already owns `loreFragments` placement) — the
  plotline editor's vision tab authors the *content*, room_scene_editor keeps
  authoring *placement*, same split already established between
  `cutscene_editor.html` (content) and `room_scene_editor.html`
  (`cutsceneTriggers[]` placement).

## 3. Quest/side-objective data model

Currently zero data shape exists (`questState`/`sideQuest` — confirmed no
matches anywhere in `game/*.js`). This needs the schema designed before any
editor UI makes sense.

```js
// game/quests.js (new)
const QUESTS = {
  pacifist_ally_arc: {
    id: 'pacifist_ally_arc',
    npcId: 'pacifist_companion',        // -> game/npcDialogue.js entry
    region: 'pacifist_enclave',
    stages: [
      { id: 'met',        requires: null,                    onEnter: { setFlag: 'metPacifistNPC' } },
      { id: 'played_game',requires: 'met',                    onEnter: { call: 'startMinigame:mirrorMatch' } },
      { id: 'trusted',    requires: { talkCount: { npcId: 'pacifist_companion', gte: 5 } },
                                                               onEnter: { setFlag: 'pacifistRestUnlocked' } },
      { id: 'recruited',  requires: 'trusted',                onEnter: { setFlag: 'pacifistAllyRecruited' } },
    ],
  },
};
```

- `requires` is either a stage id (linear gate) or a small condition object
  (`talkCount`, `flag`, `companionState` check) — enough for the pacifist arc
  and the Temporal Warden's already-built defeat-state without inventing a
  general scripting language.
- Quest stage `onEnter` reuses the same `{setFlag}`/`{call}` shape as
  `CUTSCENES{}` steps rather than a new effect syntax — one action vocabulary
  across cutscenes, visions, and quests.
- **Region-exclusion for the Child**: the "Child can't be brought all the way
  into the region" mechanic needs one new `area.js` field, something like
  `AREAS.pacifist_enclave.companionRestricted = true`, checked at the room
  transition that leads in — auto-parks `companionState.mode` at the entrance
  rather than carrying her through. This is a small, real gameplay-code change
  this plan surfaces as a dependency, not something the editor itself does.
- **Recruiting the pacifist NPC as a field ally** implies a second
  ally-assist profile alongside the Child's (a fight-assist loop analogous to
  `companion.js`'s tether-beam logic). Per the "track only" decision on the
  Child, this plan does **not** build that mechanic — it only reserves the
  `pacifistAllyRecruited` flag and stage as the hook a future session wires
  up. Flagging this explicitly so it isn't assumed to ship for free here.
- **Editor tab**: a quest builder — stage list, drag-reorder, `requires`/
  `onEnter` forms (same preset-library + raw-escape-hatch pattern
  `cutscene_editor.js` already uses for `call` steps, reused rather than
  reinvented).
- **Persistence**: `POST /save-quests` route, patches `game/quests.js`.

## 4. NPC dialogue tool

The one genuinely new interaction primitive here is **talk-count gating** —
"if you talk a lot you can sleep there" is a repeatable, accumulating
conversation, not `cutscene.js`'s single race-to-tap choice. Needs its own
small state object:

```js
// tracked in save data alongside storyFlags
npcState = {
  pacifist_companion: { talkCount: 0, flagsSeen: [] },
};
```

- `game/npcDialogue.js` (new, bare-top-level + reads `npcState`/`storyFlags`):
  `NPC_DIALOGUE{}` keyed by npcId → ordered list of `{ requires, lines[],
  onComplete }` entries, first matching-`requires` entry plays, increments
  `talkCount`. `requires` reuses the same condition shape as quest stages
  (`talkCount.gte`, `flag`) so both tools share one mental model.
- **Editor tab**: per-NPC list of dialogue entries (reorderable, since order
  is match-priority), a live "talk counter" preview slider to test which
  entry fires at a given count — this is the one piece of real interactivity
  the tool needs, everything else is form-editing like `cutscene_editor.html`.
- **Persistence**: `POST /save-npc-dialogue` route, patches
  `game/npcDialogue.js`. `npcState` itself persists through the existing
  save/load path in `game_boot_save.js` (new key, same pattern as
  `companionState`/`storyFlags` — update both save and load paths per
  CLAUDE.md's save-data section).

## Build order

1. Story Flag Graph (read-only first cut — pure value, no new game-state risk).
2. Vision format + authoring tab (closes the text-lore-fragment gap directly).
3. Quest data model + builder tab (needed before the pacifist NPC arc can be
   represented at all).
4. NPC dialogue tool (depends on quest tab's `requires` shape being settled).
5. Wire the pacifist NPC's actual content (dialogue lines, the specific
   minigame, `companionRestricted` region flag) — content work, not tooling,
   comes after 1–4 exist.

## Gaps identified in review (added 2026-08-03, before build starts)

Found via cross-check against how comparable tools (articy:draft, Yarn Spinner,
LoomGraph, Dialoqra) and general quest-design postmortems handle the same
problems, plus a pass against this repo's own conventions. None of these
block starting §1 (Story Flag Graph, still the right first step) but several
should be resolved before §3/§4 (quests, dialogue) ship real content, since
retrofitting them after content exists is much more expensive than deciding
them now.

- **No player-facing quest/journal UI.** The plan builds `QUESTS{}` and a full
  stage-tracking model but never says how the player *sees* an active quest
  in-game — `game_hud_menus.js`'s `HUD_LAYOUT` isn't mentioned anywhere in
  this doc. A quest model with no journal means even basic playtesting
  requires opening devtools to check `storyFlags`/quest stage state. Needs at
  least a stub HUD element before the pacifist arc ships as real content, not
  necessarily before the tooling itself is built.
  **Solution**: smallest version that fits the "no boxed HUD panels" rule
  (CLAUDE.md's explicit design decisions) — not a persistent panel, a single
  transient text line (current active stage's short label) that appears
  in-world near the player on stage-advance and fades, same visual language
  as the existing pickup/ability-grant toasts already in `game_hud_menus.js`.
  Add one `HUD_LAYOUT` entry (`questToast`) rather than a new panel type.
- **No cycle/deadlock detection on the flag graph.** §1's static-scan graph
  visualizes edges but doesn't check them. With quests, dialogue, and
  cutscenes all reading/writing `storyFlags`, a `requires: flagA` gated behind
  a stage whose own `onEnter` sets `flagA` (directly or through a longer loop
  across tools) is an easy mistake to make once three different editors write
  to the same namespace. This is precisely the "cycle with no exit" defect
  class that narrative-QA literature flags as the top structural bug in
  branching content — the graph should surface it, not just draw it.
  **Solution**: standard DFS-based cycle detection over the same directed
  edge list §1 already builds (three-color/white-gray-black marking —
  O(V+E), trivial at this graph's size). Run it as part of the same static
  scan that generates the graph, report cycles the same way `roomVerify.js`
  reports issues (a typed list with node ids), and surface it as a health
  indicator in the graph tab the same way `dev_hub.html` shows a health dot
  for room linter issues — don't build a second, separate "validation" UI.
- **No unreachable-content / dead-flag audit.** Related but distinct from the
  above: a flag with writes but no reads (dead state, wasted authoring) and a
  flag with reads but no writes (a bug — something gates on state nothing
  ever sets) are both mechanically detectable from the same static scan §1
  already does. `room_verify.html`/`roomVerify.js` already does exactly this
  class of check for room reachability — same philosophy applies here and
  should reuse the "linter over hand-authored" pattern rather than being a
  separate ad hoc check.
  **Solution**: two O(V) passes over the same node list as the cycle check —
  in-degree 0 (never written, only read: likely a typo or an unbuilt
  writer) and out-degree 0 (written, never read: dead authoring). Same
  report format/UI as the cycle check above; both are cheap enough to run
  on every load of the graph tab, not a separate "run linter" button.
- **No reachability audit against this game's own irreversible-choice
  pattern.** CLAUDE.md names irreversible, consent-gated choices as an
  intentional, load-bearing throughline (Void Tether, Hollow Core, the
  pacifist region itself). That means a quest or dialogue node can go
  permanently unreachable the moment a player makes an unrelated irreversible
  choice elsewhere (e.g. a stage that requires `companionState` fields the
  Void Tether leave permanently clears). The flag graph's static scan can't
  catch this by construction — it needs an explicit cross-check pass, or at
  minimum a manually-flagged "irreversible" tag on choices that the graph can
  warn about when something downstream still depends on the state it clears.
  **Solution**: the manually-flagged-edge approach is the right-sized one —
  a general auto-detector would need to model full game-state reachability,
  far beyond this tool's scope. Concretely: an `irreversible: true` field on
  the specific `CUTSCENES{}` `choice` branches and quest/dialogue effects
  already known to be one-way (Void Tether leave, Hollow Core path, the
  pacifist-region companion-park), authored by hand since there are only a
  handful. The graph pass then does one more cheap check: for each
  irreversible edge, does any node reachable *only* through it have
  dependents that assume state the edge clears? Small, targeted, matches the
  "content registry + build-time lint" pattern the branch-safe-quest-design
  literature describes rather than a general softlock solver.
- **No interaction with `LORE_ENABLED`.** Visions are explicitly built to
  replace text lore fragments, and CLAUDE.md documents the existing
  `loreFragments` text-popup system as disabled (`LORE_ENABLED = false`,
  `game_state.js`) pending a redesign as environmental storytelling. This plan
  never says whether visions ship gated behind the same flag, a new one, or
  unconditionally — that's a real decision, not an implementation detail, and
  building vision content without deciding it risks either shipping narrative
  content nobody sees (if still gated off) or accidentally re-enabling the
  disabled system's intent through a side door.
  **Solution**: reuse the existing `LORE_ENABLED` flag rather than adding a
  second one — visions are pitched in this same plan as *replacing* text lore
  fragments, so they inherit the same on/off semantics until someone
  explicitly decides otherwise; a second flag would just create two disabled
  switches for one conceptual feature. Gate vision playback in
  `game_update.js` behind `LORE_ENABLED` the same way the text-popup path is
  gated today, and say so explicitly in this plan rather than leaving it
  implicit. Content can still be authored/saved with the flag off — only
  playback is gated, same as today.
- **`npcState` reset path incomplete.** CLAUDE.md's save-data section
  requires three synchronized paths for new persisted state: save, load, and
  `startNewGame()`'s reset. §4 only mentions save/load. Without an explicit
  reset, a New Game could inherit a stale `talkCount` from a previous save
  cycle depending on how slot state is initialized — worth stating explicitly
  given this is exactly the kind of easy-to-miss third path CLAUDE.md calls
  out by name.
  **Solution**: follow the exact precedent already in `game_boot_save.js`'s
  `respawnPlayer`/new-game reset block, which explicitly zeroes every
  `companionState` field one line at a time (`companionState.active = false;`
  etc., ~line 707). Add the same for `npcState`: reset every known NPC's
  entry to `{ talkCount: 0, flagsSeen: [] }` in that same block, not a
  separate one.
- **No save migration for pre-existing saves.** Separate from the reset-path
  gap above: a save file written *before* this feature exists will load with
  `npcState === undefined`. Any `talkCount.gte` check needs a defined default
  on load, not just on new-game start, or existing saves will throw or
  silently mis-evaluate every gated condition.
  **Solution**: same defensive-load pattern already used for `companionState`
  in the load path (`companionState.active = !!(data.companion &&
  data.companion.active)`, ~line 539) — `npcState[id] = (data.npcState &&
  data.npcState[id]) || { talkCount: 0, flagsSeen: [] }` per known NPC id.
  No new pattern needed, just apply the one this file already has.
- **No debug tool integration.** CLAUDE.md is explicit that new game-state
  shapes need a debug_v1.html pass ("If you touch input handling, area data
  shape, or add new game state, run the relevant debug page"). This plan adds
  three (`quests.js`, `npcDialogue.js`, `visions.js`) and never mentions
  extending debug_v1.html's R-checks to walk them, the same way R09–R11
  already walk rooms.
  **Solution**: one new check, same shape as R11 (which already delegates to
  `RoomVerify.verifyRoom()` rather than reimplementing linting inline per
  engineering_todo.md item 6) — have it call the same cycle/dead-flag/
  reachability checks §1's graph tab runs, exposed as a plain function
  (`PlotlineVerify.verify()`) the graph tab and `debug_v1.html` both call,
  rather than writing the check twice in two different UIs.
- **No in-editor way to jump to/simulate a quest or vision state for QA.**
  The dialogue tab's talk-count preview slider is the one good example of
  this in the plan — the quest and vision tabs have no equivalent. Testing a
  late-stage quest condition or a specific vision currently means manually
  satisfying every real prerequisite in a live session.
  **Solution**: generalize the dialogue tab's slider into one small shared
  widget (a "preview as" bar: pick a quest stage or vision id from a
  dropdown, click Preview) reused across all three tabs rather than three
  bespoke implementations — same "one shared piece of interactivity" scoping
  the plan already applies to the dialogue tab specifically.
- **Undo/redo omitted.** `levelEditor.html` and `room_scene_editor.html` both
  use the shared `undoHistory.js` IIFE utility (per CLAUDE.md's architecture
  map). This plan's four tabs are all list/form editors with reordering
  (dialogue entries, quest stages) — exactly the editing pattern where an
  accidental delete or drag-reorder without undo is costly. Should reuse
  `undoHistory.js`, not skip it or reinvent it.
  **Solution**: confirmed 11 of the existing `editor/*` tools already wire up
  `UndoHistory.create(getState, setState)` (`levelEditor.html`,
  `room_scene_editor.html`, `anim_editor.html`, `hud_editor.html`,
  `combo_editor.html`, `inventory_editor.html`, `enemy_designer.html`,
  `cutscene_editor.html`/`.js`, `exportPanel.js`) — this isn't a new pattern
  to design, just apply the same `getState`/`setState` wrapper per tab's own
  data object (`QUESTS`, `NPC_DIALOGUE`, `VISIONS`, flag-meta), same as
  `levelEditor.html`'s reassignable-`let` case per engineering_todo.md's own
  note on that migration.
- **No "Diff vs Saved" for the four new save routes.** `levelEditor.html` has
  this explicitly for its own save route; the plan's `POST
  /save-story-flags`, `/save-visions`, `/save-quests`, `/save-npc-dialogue`
  routes don't mention it, despite following the same patch-and-backup
  pattern as routes that do.
  **Solution**: lower priority than the above since only `levelEditor.html`
  has this today (not yet a suite-wide convention — see the broader
  persistence-inconsistency finding below), but cheap to add here: a plain
  `JSON.stringify(current) !== JSON.stringify(lastSavedSnapshot)` check
  shown as a modal or inline diff, gating the save button's enabled state
  the same way `levelEditor.html` already does.
- **No localization consideration.** Every comparable professional tool
  (articy:draft, Yarn Spinner) treats dialogue/quest/vision text as
  externalizable-by-design specifically because translation is usually needed
  eventually. Not a build-now requirement, but storing lines as inline
  strings in `npcDialogue.js` rather than behind a lookup-by-id is a decision
  this plan makes implicitly (via its own code sample) rather than
  consciously — worth a one-line explicit call rather than defaulting into it.
  **Solution**: explicit decision, not deferred — keep inline strings for
  v1. Nothing else in this codebase has i18n today (no other file does
  string externalization), so building a lookup-by-id layer now is
  speculative infrastructure for a need that doesn't exist yet, which
  CLAUDE.md's own engineering rules argue against ("don't design for
  hypothetical future requirements"). The only future-proofing worth doing
  now, since it's free: give every dialogue line/vision step/quest stage a
  stable `id` field (already implied by the plan's own schemas) rather than
  addressing lines by array index — that alone is what makes a later
  extraction pass tractable, without building the extraction layer itself.
- **`save-server.js` has no code path for creating a new file.** Checked the
  actual implementation, not just the pattern description: today's server
  only has two `LAYOUTS` entries (`/save-hud-layout`, `/save-inventory-
  layout`), and `patchLayoutBlock()` works by finding an *existing* `const
  DECLNAME = {` line in an *existing* target file and patching lines inside
  it — it has no "file doesn't exist yet, scaffold it" branch. Every other
  content editor (`levelEditor.html`, `room_scene_editor.html`,
  `cutscene_editor.html`, `combo_editor.html`, `anim_editor.html`) actually
  uses the manual copy-paste "Export JSON" flow, not a live save route —
  the HUD/inventory routes are the only two tools with real disk-write
  today. This plan's four new routes (`/save-story-flags`, `/save-visions`,
  `/save-quests`, `/save-npc-dialogue`) target `game/quests.js`,
  `game/npcDialogue.js`, and `game/visions.js` — **files that don't exist
  yet**. Describing these as following "the same line-patch + timestamped
  backup pattern as the existing HUD/inventory routes" is accurate for the
  patch *mechanism* but skips over the fact that mechanism has never been
  used to create a file from nothing.
  **Solution**: add one new small code path to `save-server.js` — if
  `targetFile` doesn't exist, write a minimal starter (`// auto-generated
  scaffold\nconst DECLNAME = {\n};\n`) before running the existing patch
  logic against it, so the rest of `patchLayoutBlock()` works unmodified.
  Do this once, generically, rather than four times per-route.

## Open questions / explicitly out of scope

- Which minigame (of the "5 minigames" `regions.md` already mentions) is *the*
  one played with this NPC specifically, versus the other four being
  ambient/optional — not decided, not needed to build the tooling.
- The pacifist ally's actual fight-assist mechanics (if any) once recruited —
  deferred, per the Child track-only decision extending to consistency here.
- Whether `npcState` generalizes to a full relationship/trust *system*
  (multiple thresholds, decay, etc.) beyond a flat `talkCount` — start with
  the flat counter, only generalize if a second NPC actually needs something
  richer than gte-thresholds.
